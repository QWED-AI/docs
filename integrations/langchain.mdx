## Installation

```bash
pip install qwed langchain
```

## Quick start

```python
from qwed_sdk.langchain import QWEDTool, QWEDVerificationCallback

# Add QWED as a tool
from langchain.agents import initialize_agent, AgentType
from langchain.llms import OpenAI

agent = initialize_agent(
    tools=[QWEDTool()],
    llm=OpenAI(),
    agent=AgentType.ZERO_SHOT_REACT_DESCRIPTION,
)

result = agent.run("Verify: Is 2+2 equal to 5?")
# Agent uses QWED tool to verify and corrects the answer
```

## Available components

### QWEDTool

General-purpose verification tool:

```python
from qwed_sdk.langchain import QWEDTool

tool = QWEDTool(api_key="qwed_...")
print(tool.run("2+2=4"))
# ⚠️ HOLDS, NOT ADMITTED: the claim holds for the translated expression ..., but it was
# translated from your query by an LLM, and that translation is not verified.
```

From v10.0.0, `QWEDTool` reports this way. It sends the query to `/verify/natural_language`, which doesn't admit a result while the LLM translation of the query is unverified. So the tool reports what holds or fails for the translated expression instead of `✅ VERIFIED`. A false claim is `❌ INCORRECT` with the calculated value when the server sends one.

### Specialized tools

```python
from qwed_sdk.langchain import QWEDMathTool, QWEDLogicTool, QWEDCodeTool

tools = [
    QWEDMathTool(),   # Math expressions
    QWEDLogicTool(),  # QWED-Logic DSL
    QWEDCodeTool(),   # Code security
]
```

From v10.0.0, the tools call a result incorrect or unsafe only when QWED decided it. An `UNVERIFIABLE` or `BLOCKED` result, such as input that doesn't parse, a timeout or a server the client could not reach, returns its status and the server's message, for example `⚠️ UNVERIFIABLE: ...` or `⛔ BLOCKED: ...`. `QWEDCodeTool` lists the issues the server reports for unsafe code (`- CRITICAL: ...`). A tool answer starts with `✅` only when the server admitted the result.

### QWEDVerificationCallback

Auto-verify all LLM outputs:

```python
from langchain.chains import LLMChain
from qwed_sdk.langchain import QWEDVerificationCallback

callback = QWEDVerificationCallback(
    verify_math=True,
    verify_code=True,
    verify_sql=True,
    log_results=True,
    sql_schema_ddl="CREATE TABLE users (id INT, name TEXT)",
    sql_dialect="sqlite",
)

chain = LLMChain(
    llm=OpenAI(),
    prompt=prompt,
    callbacks=[callback]
)

result = chain.run("Calculate 15% of 200")
# [QWED] ✅ MATH: verified=True
```

<Info>
New in v10.0.0: `sql_schema_ddl`, `sql_dialect` and the checks below. In 9.x, the callback takes no SQL schema.
</Info>

The callback checks what it recognises in each output:

- **Fenced blocks.** Every fenced block is checked. A block tagged `sql` or a SQL dialect (`postgresql`, `postgres`, `pgsql`, `mysql`, `sqlite`, `tsql`, `plsql`) is checked as SQL, in `sql_dialect`. A block with another tag is checked as code in that language. An untagged block that starts with a SQL statement gets both checks, and a check that can't parse it doesn't count when the other check parsed it. Any other untagged block is checked as Python.
- **SQL needs a schema.** `/verify/sql` checks a query against the tables it runs on. Pass their `CREATE TABLE` statements as `sql_schema_ddl`; `sql_dialect` defaults to `sqlite`. Without a schema, the callback sends no SQL and records each SQL check as `UNVERIFIABLE`.
- **SQL outside a fenced block** that the callback recognises as a statement is recorded as `UNVERIFIABLE` when `verify_sql=True`, because the callback can't tell where it starts and ends. So is SQL in a code block when `verify_code=False`.
- **A check that raises,** for example when the server can't be reached, is recorded as `UNVERIFIABLE` with the exception type. It doesn't interrupt the LangChain run.

Each SQL or code record has `verified` and the route's `status`. A code record's `vulnerabilities` is the number of `issues` the route sent. `get_summary()` counts an output as verified only when at least one check ran on it and every check verified it. Claims in prose that the callback doesn't recognise aren't checked, so a verified output is one whose checks all passed, not one checked in full.

### QWEDVerifiedChain

Wrap any chain with verification:

```python
from qwed_sdk.langchain import QWEDVerifiedChain

base_chain = LLMChain(llm=llm, prompt=prompt)
verified_chain = QWEDVerifiedChain(base_chain, auto_correct=True)

result = verified_chain.run("What is 2+2?")
print(result.output)    # "4"
print(result.verified)  # True
```

The tools, callback, and `QWEDVerifiedChain` read the client's `is_verified`, which follows the server's admission. `result.verified` is `True` only when the server admitted the output. A `BLOCKED` or `UNVERIFIABLE` result is never verified.

<Warning>
Before v8.0.0 ([GHSA-83v6-6h23-pvp4](https://github.com/QWED-AI/qwed-verification/security/advisories/GHSA-83v6-6h23-pvp4)), the integrations read a `verified` attribute that `QWEDClient` results don't have, so their checks raised. When you call `QWEDClient` directly, gate on `result.is_verified`.
</Warning>

## LCEL integration

Use with LangChain Expression Language:

```python
from langchain_core.runnables import RunnableLambda

def verify_output(text):
    from qwed_sdk import QWEDClient
    client = QWEDClient()
    result = client.verify(text)
    return text if result.is_verified else f"[UNVERIFIED] {text}"

chain = prompt | llm | RunnableLambda(verify_output)
```

## Best practices

1. **Use callbacks for monitoring** — Track verification rates
2. **Use tools for agent autonomy** — Let agents verify themselves
3. **Use wrappers for guarantees** — Ensure all outputs are verified
