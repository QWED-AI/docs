The Consensus Engine runs several verification engines on one query, with fault tolerance. Its result is advisory only.

<Warning>
**Consensus is advisory only (releases after v11.0.0).** Every engine decides a model's translation of your query, and the query states no claim of yours, so engines that agree have not verified anything. `/verify/consensus` returns `UNVERIFIABLE` or `BLOCKED`, never `VERIFIED`, in every mode. Every response carries `advisory_only: true` and `meets_requirement: false`, its `proof_ref` is always `null`, and none carries an attestation. Use the result as a signal for review, not as a verification.
</Warning>

<Warning>
**Changed in v4.0.4:** Python code verification within consensus now runs exclusively through the secure Docker executor (`SecureCodeExecutor`). If the Docker sandbox is unavailable, consensus returns a `blocked_secure_execution` status and the API responds with HTTP 503. From v6.0.0, the API responds with HTTP 200 and `BLOCKED` instead.
</Warning>

## Features

- **Async parallel execution** — Run engines concurrently
- **Circuit breaker** — Temporarily excludes engines that time out or raise errors
- **Engine health monitoring** — Track reliability
- **Weighted consensus** — Consider engine reliability
- **Secure code execution** — Python engine runs through the Docker sandbox only

## Usage

```python
from qwed_sdk import QWEDClient

client = QWEDClient(api_key="qwed_...")

result = client.verify_with_consensus(
    query="2 + 2 = 4",
    mode="high"  # single, high, maximum
)

print(result.final_answer)     # 4
print(result.confidence)       # 0.0
print(result.engines_used)     # 2
print(result.agreement_status) # "no_independent_verification"
```

<Info>Changed in v10.0.0</Info>

One engine is not a consensus. In the example, SymPy verifies the answer and the Python engine is advisory only, so the answer has been verified by one engine alone. The result is `BLOCKED` with `constraint_id: "consensus.no_independent_verification"` and `confidence: 0.0`.

When two distinct engines verify, the result is still not `VERIFIED`. It is `UNVERIFIABLE`, because consensus is advisory only.

## Verification modes

| Mode      | Engines             | Speed  | Confidence | Docker required |
| --------- | ------------------- | ------ | ---------- | --------------- |
| `single`  | 1 (SymPy)           | ⚡ Fast | No consensus: one engine | No              |
| `high`    | 2 (SymPy + Python)  | Medium | No consensus: Python is advisory only | Yes             |
| `maximum` | 3+ (All applicable) | Slower | Advisory: never `VERIFIED` | Yes             |

<Note>
The `high` and `maximum` modes include the Python engine, which requires the secure Docker sandbox. If Docker is unavailable, these modes return `blocked_secure_execution` instead of falling back to in-process execution. This status takes precedence over `no_independent_verification`, so it is returned even when SymPy verified the answer. The `/verify/consensus` response is then `BLOCKED` with HTTP 200, not an HTTP error.
</Note>

## Async execution

```python
import asyncio

async def verify_many():
    results = await asyncio.gather(
        client.verify_async("2+2=4"),
        client.verify_async("3*3=9"),
        client.verify_async("sqrt(16)=4")
    )
    return results
```

## Circuit breaker

The circuit breaker excludes an engine that stops answering. It measures engine health, not verdicts:

- **A verdict is never a failure.** An engine that returns a result within the [execution deadline](#execution-deadlines-and-partial-results) counts as healthy, whatever it decides: a wrong claim, an unsatisfiable model or a question it cannot use.
- **Only an engine that does not answer counts as a failure:** a timeout, or an exception the engine does not handle.
- **Three consecutive failures open the circuit for 30 seconds.** During that time the engine is skipped and recorded as a `BLOCKED` result with the error `Engine excluded by open circuit breaker`. A skipped engine records no new failure. After 30 seconds the engine is `degraded` and runs again, and one success returns it to `healthy`. Any success resets the count of consecutive failures. While the engine is `degraded`, one more failure opens the circuit again for another 30 seconds, because only a success resets the count.
- **The breaker is shared by every request handled by the same server process.** One caller's timeouts can exclude an engine for every other caller until the circuit closes.

Before this fix, an engine's verdict counted as a failure, so three wrong claims in a row opened SymPy's circuit for 30 seconds for every caller.


```python
# Check engine health
health = client.get_engine_health()

print(health)
# {
#   "SymPy": {"state": "healthy", "failures": 0},
#   "Python": {"state": "healthy", "failures": 0},
#   "Z3": {"state": "open", "failures": 3}
# }

# Reset circuit breakers
client.reset_circuit_breakers()
```

## Execution deadlines and partial results

Consensus verification runs under a single 30-second aggregate deadline that covers all engines. No engine call can hold a request open indefinitely, and `/verify/consensus` never hangs or returns HTTP 500 because one engine stalled.

How the deadline applies:

- **One aggregate budget, not per-engine stacking.** All selected engines share the same 30-second wall clock. Sequential per-engine waits cannot accumulate beyond it.
- **Timed-out engines become explicit `BLOCKED` results.** An engine that misses the deadline is recorded in `verification_chain` as a `BLOCKED` `EngineResult` with the timeout in its `error` field (for example, `"Engine timed out after 30s"`). The failure is also recorded with the circuit breaker.
- **Circuit-open engines are recorded too.** An engine skipped because its circuit breaker is open appears as a `BLOCKED` result rather than being silently dropped.
- **Partial results still aggregate.** Engines that finished within the deadline contribute normally. The consensus verdict is computed from the results that arrived, with the fail-closed [status propagation](#status-propagation) rules applied. The consensus is `UNVERIFIABLE`, or `BLOCKED` when every engine is blocked or only one engine verified.
- **Off the event loop.** Engine execution runs in a dedicated per-call executor, so a slow consensus request degrades only itself, not other API traffic.

```python
result = client.verify_with_consensus(query="2 + 2 = 4", mode="maximum")

for engine in result.verification_chain:
    if engine.status == "BLOCKED" and "timed out" in (engine.error or ""):
        print(f"{engine.engine_name} missed the 30s deadline")
```

<Note>
A consensus response that includes timed-out engines is a valid partial result, not an error. Check `verification_chain` to see which engines contributed and treat the aggregate `status` as authoritative.
</Note>

## Async failure handling

When an unexpected error occurs during async engine aggregation, the Consensus Engine records the failure as a dedicated `EngineResult` entry rather than silently dropping it. This ensures that:

- The failure is visible in the `results` array returned to the caller
- Aggregate confidence scores account for the failed engine
- The error is logged via `logger.exception` for post-mortem debugging

The recorded result uses `engine_name: "consensus_orchestrator"`, `method: "async_aggregation"`, `success: false`, and includes the error message in the `error` field.

## Secure execution gates

Before any Python code runs in the Docker sandbox, two validation layers apply. Both fail closed: a rejected input returns a security error instead of executing.

### Single-expression gate on translated math

When consensus translates a natural-language math query, the translated expression is interpolated into the generated verification code. The translator therefore enforces that the output is exactly one Python expression:

- The expression must parse with `ast.parse(..., mode="eval")`. Multi-statement input, semicolon chains, assignments, imports, and multi-line newline smuggling all fail by construction.
- Expressions longer than 500 characters are rejected before parsing, so deeply nested adversarial input never reaches the parser.
- The existing character-set and denylist checks remain as defense in depth.

Bracketed multi-line expressions (a single expression wrapped in parentheses across lines) still pass. Anything that is not one expression does not.

### Module-indirection blocklist on executed code

The pre-execution AST check on sandboxed Python code inspects every dotted segment, not just the first:

- **Imports** of OS, process, and reflection modules (`os`, `sys`, `subprocess`, `socket`, `posix`, `nt`, `importlib`, `ctypes`, `builtins`, and network clients) are blocked wherever the module name appears in the import path, including `from ... import os as safe` aliasing.
- **Attribute chains** are blocked when any segment names a dangerous module, so package-internal re-exports (reaching the OS module through pandas or numpy internals) are caught even though the chain is rooted at an innocuous alias.
- **OS-primitive calls** (`system`, `popen`, `import_module`, the `exec*`/`spawn*` families, `fork`) are blocked as bare names and as attribute targets, which also stops `importlib.import_module("os")`-style indirection.

Legitimate pandas and numpy verification code at the public API surface (`np.linalg.norm`, `pd.Timestamp.now`) is unaffected.

### Runtime module and builtin allowlist

Since v7.3.0, sandboxed code also runs in an isolated namespace inside the container. This runtime layer applies even if code gets past the static checks:

- **Imports are limited to an allowlist** of analysis modules (the same allowlist the [Stats engine](/engines/stats#runtime-module-and-builtin-allowlist) uses): `numpy`, `pandas`, `scipy`, `sklearn`, `statsmodels`, `patsy`, `math`, `cmath`, `statistics`, `decimal`, `fractions`, `random`, `datetime`, `json`, `re`, `collections`, `itertools`, `functools`, `operator`, `array`, `bisect`, `heapq`, `string`, and `typing`. Importing any other module, or using a relative import, raises `ImportError` and the execution fails.
- **Builtins are reduced to safe names.** `eval`, `exec`, `compile`, `getattr`, `setattr`, `delattr`, `vars`, `globals`, `locals`, `open`, `input`, and `memoryview` are not available.
- **`np`/`numpy` and `pd`/`pandas` are pre-bound**, so generated code doesn't need to import them. Assign the output to `result`.

```python
# Runs: allowlisted modules only
import math
result = math.isclose(0.1 + 0.2, 0.3)

# Fails: os is not on the allowlist
import os  # ImportError: import of 'os' is not permitted in the sandbox (GHSA-j3x4)
```

<Warning>
**Behavior change in v7.3.0.** Sandboxed code that imported a module outside the allowlist now fails. Rewrite it to use the allowlisted modules. See [GHSA-j3x4-v3p2-4mq3](https://github.com/QWED-AI/qwed-verification/security/advisories/GHSA-j3x4-v3p2-4mq3).
</Warning>

## Engine selection

The consensus engine automatically selects which engines to run based on the verification mode:

| Mode      | Engines selected                    |
| --------- | ----------------------------------- |
| `single`  | SymPy                               |
| `high`    | SymPy, Python                       |
| `maximum` | SymPy, Python, Z3 (+ Stats for statistical queries) |

### Z3 engine in `maximum` mode

The Z3 engine proves a claim, as [`/verify/logic`](/engines/logic) does. The model translates the query into constraints and a claim, and Z3 decides whether the claim follows from the constraints. Before this fix, the Z3 engine failed on every query and was recorded as `BLOCKED`.

| Z3 outcome | Z3 engine status |
| ---------- | ---------------- |
| The claim follows from the constraints (`VALID`) | `VERIFIED` |
| Z3 finds a counterexample (`INVALID`) | `UNVERIFIABLE` |
| The constraints cannot all hold (`VACUOUS`) | `UNVERIFIABLE` |
| Z3 does not decide (`UNKNOWN`) | `UNVERIFIABLE` |
| The translation states no claim | `UNVERIFIABLE` |
| The translation is refused, for example an unsupported goal, or Z3 cannot run the proof | `BLOCKED` |

The Z3 engine's `VERIFIED` is its own verdict on the translated claim, shown in `verification_chain`. It cannot make the consensus `VERIFIED`. Z3 decides whether a claim holds, not a value, so it does not vote on the answer. It still counts as an engine that verified: when SymPy and Z3 both verify, the consensus is `UNVERIFIABLE`, and when only Z3 verifies, the consensus is `BLOCKED` with no `final_answer`.

The Z3 solve runs on the same dedicated thread as `/verify/logic` solves and is bounded by `QWED_Z3_TIMEOUT` (default 15 seconds), counted from when the solve is queued. A solve that does not finish in time is recorded as a `BLOCKED` Z3 result and as a failure with the [circuit breaker](#circuit-breaker). Its `error` in `verification_chain` reads `Engine execution failed`, not a timeout message, so a check for `"timed out"` like the example above does not catch it. The 30-second consensus deadline still applies to the whole engine run, translation included.

<Note>The fact engine is excluded from automatic engine selection. Fact verification requires external context, and including it in consensus without that context would create self-referential verification loops. If fact verification is invoked during consensus, it returns an error indicating that external context is required.</Note>

## Consensus calculation

The engine weights each answer by engine reliability:

| Engine | Reliability Weight |
| ------ | ------------------ |
| SymPy  | 1.00               |
| Python | 0.99               |
| Stats  | 0.98               |

Final confidence = weighted average of agreeing engines. Z3 does not vote on the answer (see [Z3 engine in `maximum` mode](#z3-engine-in-maximum-mode)). Agreement and confidence never make the result `VERIFIED`.

### Agreement statuses

| Status | Meaning |
| ------ | ------- |
| `unanimous` | All engines returned the same answer |
| `majority` | More than half of the total weight agrees |
| `split` | No clear majority among engines |
| `no_results` | No engines returned a result |
| `all_failed` | No engine succeeded and not every engine was blocked, for example when SymPy finds the answer wrong. The result is `UNVERIFIABLE` |
| `no_answer` | No engine that computes an answer succeeded, so there is no answer to vote on (Z3 does not vote). The result is `UNVERIFIABLE`. When Z3 is the only engine that verified, the status is `no_independent_verification` instead, and the result is `BLOCKED` |
| `blocked` | Every engine returned `BLOCKED`, or the prompt-injection check refused the query before any engine ran (`engines_used` `0`). The result is `BLOCKED` |
| `no_independent_verification` | Only one engine verified the answer. The result is `BLOCKED` with `confidence` `0.0` |
| `blocked_secure_execution` | The Docker sandbox is unavailable and a required engine cannot run. The result is `BLOCKED` (HTTP 200). It takes precedence over every status that engine results produce, `no_independent_verification` included |

## Status propagation

Consensus is advisory, not a proof engine. Per the [3-tier engine classification](/engines/overview), the consensus result is `UNVERIFIABLE` or `BLOCKED`, never `VERIFIED`:

- The prompt-injection check refuses the query → the consensus result is `BLOCKED` with `agreement_status` `blocked` and no answer. This check runs before any engine is selected, so no engine runs, none answers the query and none records a failure with its circuit breaker. It is the check `/verify/natural_language` applies, so it also refuses a query over 2,000 characters or one that contains words such as `mode`, `root` or `system`.
- The Python engine finds the Docker sandbox unavailable → the consensus result is `BLOCKED` with `agreement_status` `blocked_secure_execution`, whatever the other engines returned. This rule is checked first among engine results.
- All engines return `BLOCKED` → the consensus result is `BLOCKED`.
- Otherwise, only one engine verifies the answer → the consensus result is `BLOCKED` with `constraint_id: "consensus.no_independent_verification"` and `confidence` `0.0`, whatever the other engines returned (advisory, blocked or absent). One engine is not a consensus.
- Otherwise → the consensus result is `UNVERIFIABLE`, whether the engines agree or not and however many verified. Before this change, a consensus was `VERIFIED` only when two distinct engines verified the same answer, which no two engines did, as the Z3 engine failed on every query.
- The route passes every result through one more check: any status other than `UNVERIFIABLE` or `BLOCKED` is returned as `UNVERIFIABLE`, so the consensus `status` never reaches the response, the attestation or the audit row as `VERIFIED`. Each `verification_chain` entry keeps its engine's own status, which can be `VERIFIED`.
- Math-query translation failures fail closed — the engine raises rather than fabricating a numeric answer from a regex or decimal guess.

Individual engine outcomes are exposed via the `status` field on each `EngineResult` in the aggregated result.

### Sub-engine status contract

Not every sub-engine that runs under consensus can emit `VERIFIED`. The table below makes the fail-closed contract explicit — these engines never contribute a `VERIFIED` vote, even on a successful computation, so their output stays advisory:

| Sub-engine | Success outcome | Rationale |
| ---------- | --------------- | --------- |
| Stats (mean, median, variance) | `UNVERIFIABLE` — computed value stays on the result as advisory | Calculating a statistic is not verifying a claim. Only comparison against a claimed value with proof of correctness can produce `VERIFIED`. |
| Python code execution | `UNVERIFIABLE` — captured output stays on the result as advisory | Runtime success only disproves by crashing; executing an expression is not proving its result matches the query's semantics. |

This mirrors the existing [Fact engine](/engines/fact) heuristic contract: a TF-IDF `SUPPORTED` verdict is capped at `UNVERIFIABLE` because heuristic support is not a proof. A query answered only by Stats or code execution stops at `UNVERIFIABLE`, with the computed value carried through as advisory data.

## ConsensusResult

Async and sync consensus verification both return a `ConsensusResult` dataclass that carries the aggregated verdict along with per-engine detail:

| Field | Type | Description |
| ----- | ---- | ----------- |
| `final_answer` | `Any` | Best-supported answer across engines |
| `confidence` | `float` | Weighted confidence, `0.0`–`1.0` |
| `agreement_status` | `str` | `unanimous`, `majority`, `split`, `no_results`, `all_failed`, `no_answer`, `blocked`, `no_independent_verification`, or `blocked_secure_execution` |
| `engines_used` | `int` | Number of engines that returned a result |
| `verification_chain` | `List[EngineResult]` | Per-engine outcomes, including each engine's `status` |
| `total_latency_ms` | `float` | End-to-end latency for the aggregation |
| `parallel_execution` | `bool` | True when engines ran concurrently |
| `status` | `Optional[DiagnosticStatus]` | Trust-boundary status: `UNVERIFIABLE` or `BLOCKED` (enum, not a bare string). Never `VERIFIED` |
| `proof_ref` | `Optional[str]` | Always `None`. Kept so code that reads it keeps working |
| `verified_evidence` | `Optional[Dict[str, Any]]` | Always `None`. Kept so code that reads it keeps working |

<Info>
`status` is now a [`DiagnosticStatus`](/advanced/diagnostics) enum rather than a bare string. Code that compared `result.status == "BLOCKED"` should use `result.status is DiagnosticStatus.BLOCKED` or check `result.status.value` for the string form.
</Info>

### `.to_diagnostic_result()`

`ConsensusResult` converts to a [`DiagnosticResult`](/advanced/diagnostics) that is `UNVERIFIABLE` or `BLOCKED`, with `advisory_only: true` in its developer fields:

```python
result = client.verify_with_consensus(query="2 + 2 = 4", mode="high")

dr = result.to_diagnostic_result()

dr.is_verified          # False: a consensus is never verified
dr.proof_ref            # None
dr.developer_fields     # {'agreement_status': 'no_independent_verification', 'confidence': 0.0, 'engines_used': 2, 'advisory_only': True, 'constraint_id': 'consensus.no_independent_verification'}
```

The conversion is fail-closed: a `ConsensusResult` whose `status` says `VERIFIED`, such as one built by hand, converts to `UNVERIFIABLE`. The `/verify/consensus` endpoint's `meets_requirement` flag is always `false`, on every response. Confidence alone is never sufficient.
