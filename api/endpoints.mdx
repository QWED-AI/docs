## Base URL

QWED has no hosted API. Use the address of the QWED server you run; locally it is:

```text
http://localhost:8000
```

## Health check

### GET /health

Check API status. No authentication required.

```bash
curl http://localhost:8000/health
```

**Response:**

```json
{
  "status": "healthy",
  "service": "QWED Platform",
  "version": "5.1.0",
  "timestamp": "2024-12-20T12:00:00Z"
}
```

### GET /health/identity

Challenge-response proof that the server holds a given secret set. `qwed init` calls this endpoint before bootstrapping an API key to confirm it's talking to the right local server. See [`qwed init`](/advanced/cli#qwed-init-onboarding-and-bootstrap). No authentication required.

**Query parameters:**

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `nonce` | string | Yes | Caller-generated random value, 1–128 characters. Use a fresh nonce for every request. |

```bash
# Fresh random value per request, e.g. Python's secrets.token_urlsafe(24)
curl http://localhost:8000/health/identity?nonce=Vh8Qm2xT-0pLw6KdYs3rZbNf_5JtAe1X
```

**Response:**

```json
{
  "identity": {
    "jwt_hmac": "9f2c...e41a",
    "lookup_hmac": "b07d...5c13",
    "audit_hmac": "4e8a...d270"
  }
}
```

| Field | Description |
|-------|-------------|
| `identity.jwt_hmac` | Hex HMAC-SHA256 under `QWED_JWT_SECRET_KEY` of the message `qwed-server-identity-v1:jwt:<nonce>` |
| `identity.lookup_hmac` | Hex HMAC-SHA256 under `QWED_API_KEY_LOOKUP_SECRET` of the message `qwed-server-identity-v1:lookup:<nonce>` |
| `identity.audit_hmac` | Hex HMAC-SHA256 under `QWED_AUDIT_SECRET_KEY` of the message `qwed-server-identity-v1:audit:<nonce>` |

To verify, compute the same HMACs with your local secrets and compare them in constant time. The secrets themselves are never returned.

**Error responses:**

| Status | Detail | Cause |
|--------|--------|-------|
| `400` | `nonce is required (max 128 characters)` | `nonce` is missing, empty, or longer than 128 characters |
| `503` | `server secrets not configured` | The server has no `QWED_JWT_SECRET_KEY`, `QWED_API_KEY_LOOKUP_SECRET`, or `QWED_AUDIT_SECRET_KEY` set |

Servers released before this endpoint existed return `404`.

## Request limits

Every `/verify` route enforces a request body cap. QWED rejects an oversized body before the handler reads or parses it.

| Route | Body cap |
|-------|----------|
| JSON routes: `/verify/natural_language`, `/verify/logic`, `/verify/fact`, `/verify/code`, `/verify/math`, `/verify/sql`, `/verify/rag`, `/verify/process`, `/verify/consensus`, `/verify/batch` | 1,000,000 bytes |
| `/verify/stats` (multipart upload) | 10,000,000-byte file plus 64 KiB envelope headroom |
| `/verify/image` (multipart upload) | 10 MiB file plus 64 KiB envelope headroom |

The server also bounds slow work so one request can't stall the API for other callers. Self-hosters can tune these bounds with environment variables. See [Availability limits](/advanced/self-hosting#availability-limits).

| Status | Detail | Cause |
|--------|--------|-------|
| `408` | `Request body not received in time.` | The client didn't finish sending the body within the read deadline (10 seconds for JSON routes, 30 seconds for uploads) |
| `413` | `Request body exceeds the <N> byte limit for this endpoint.` | The body is larger than the route's cap |
| `503` | `Server busy — retry shortly.` | Too many JSON requests are in flight on this server process |
| `503` | `Upload capacity reached — retry shortly.` | Too many `/verify/stats` or `/verify/image` uploads are in flight on this server process |

Treat `503` responses from these limits as retryable. Back off and resend the request.

## Verification endpoints

### POST /verify/natural_language

Main entry point for verifying natural language queries. Routes through the QWED Control Plane with multi-tenancy support.

**Request:**

```json
{
  "query": "What is 15% of 200?",
  "provider": "openai"
}
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `query` | string | Yes | Natural language claim to verify |
| `provider` | string | No | Preferred LLM provider (e.g., `openai`, `anthropic`) |

**Response:**

The endpoint returns the [`DiagnosticResult`](/advanced/diagnostics) verdict that the control plane enforced for the translated expression, flattened with its developer fields, plus a separate `admission` decision. QWED no longer re-derives the verdict from the legacy engine dictionary, which turned every decided claim into `UNVERIFIABLE`.

```json
{
  "status": "VERIFIED",
  "agent_message": "Expression verified successfully",
  "proof_ref": "sha256:...",
  "is_authoritative": true,
  "is_valid": true,
  "calculated_value": 30.0,
  "claimed_value": 30.0,
  "translated_expression": "0.15 * 200",
  "verification_scope": "translated_expression_only",
  "query_semantics_verified": false,
  "admission": "BLOCKED",
  "developer_fields": { "...": "same fields as above" }
}
```

| Field | Type | Description |
|-------|------|-------------|
| `status` | string | Verdict for the translated expression: `VERIFIED`, `UNVERIFIABLE`, or `BLOCKED` |
| `is_valid` | boolean | `true` when the translated claim holds. A translated claim proven false is `VERIFIED` with `is_valid: false` |
| `translated_expression` | string | The expression the LLM produced and the engine evaluated |
| `verification_scope` | string | Always `"translated_expression_only"`. The verdict covers the translated expression, not your question |
| `query_semantics_verified` | boolean | Always `false`. QWED cannot prove the translation means what you asked |
| `admission` | string | Always `"BLOCKED"` (`DENY`) for this endpoint, even when the translated claim holds |

Admission is always `BLOCKED` because the LLM translation itself is unverified, so QWED never admits the result as an answer to your question. The verdict itself is unchanged. The audit log row's `is_verified` follows admission, so it is always `false`. QWED returns `BLOCKED` as the verdict when the control plane returns a malformed diagnostic or when the output sanitizer rejects the translated expression.

For a deterministic, admissible result, send the expression to [`POST /verify/math`](#post-verify-math) directly.

The control plane also builds a `trust_boundary` record that describes what the pipeline proved. The control-plane response carries the enforced verdict as `diagnostic` together with `admission`.

**`trust_boundary` fields:**

| Field | Type | Description |
|-------|------|-------------|
| `query_interpretation_source` | string | Always `"llm_translation"` |
| `query_semantics_verified` | boolean | Always `false` — QWED cannot verify that the LLM correctly interpreted the user's intent |
| `verification_scope` | string | Always `"translated_expression_only"` — the attestation and enforcement below bind to the translated expression, not the natural-language `user_query` |
| `deterministic_expression_evaluation` | boolean | `true` when the inner engine status was `VERIFIED` or `DISPROVEN` |
| `formal_proof` | boolean | Always `false` |
| `translation_claim_self_consistent` | boolean | Whether the translated expression matched its own claimed answer |
| `provider_used` | string | LLM provider used for translation |
| `trust_enforced` | string | Status returned by the mandatory trust-boundary enforcement step. Matches `overall_status`. |
| `attestation_policy` | string | Always `"mandatory"` — attestation admission is always required, never advisory |
| `attestation_error` | string | Present only when the underlying attestation failed to sign. Machine-readable code (e.g. `SIGNING_FAILURE`, `CRYPTO_UNAVAILABLE`) explaining why the response was downgraded to `BLOCKED`. |
| `overall_status` | string | Final status set from the enforced decision — never from the raw verifier verdict. Mirrors the control-plane response `status`. |

#### Mandatory attestation admission

The control plane treats attestation as an admission gate, not a decoration:

- The final `status` and `trust_boundary.overall_status` are set by `enforce_trust_decision(..., require_attestation=True)` after signing, not by the raw verifier verdict. A `VERIFIED` math result is only surfaced once `create_verification_attestation()` returns `ISSUED`.
- A translated claim proven false is signed and attested like a true one, with `verified: false` in the attestation and `is_valid: false` in the verdict.
- If attestation signing fails for any reason, the response is downgraded to `BLOCKED` (fail-closed). The attestation error code is echoed under `trust_boundary.attestation_error` and the top-level response omits the attestation token.
- The attestation `qwed.query_hash` binds to the translated expression that the deterministic engine actually evaluated — not to the natural-language `user_query`. This matches the disclosed `verification_scope: "translated_expression_only"`: the natural-language query still appears in `response.user_query` for display, but downstream consumers verifying the attestation should hash the translated expression, not the user prose.

See [Cryptographic attestations](/advanced/attestations) for the full `AttestationResult` contract and [Trust boundary](/engines/math#trust-boundary) for the math-engine discussion.

<Note>
The LLM provider call runs off the server's event loop under `QWED_PROVIDER_TIMEOUT` (default 30 seconds). If the provider doesn't respond in time, the request fails closed with an `ERROR` status instead of stalling other requests.
</Note>

### POST /verify/math

<Info>Updated in v5.1.0: `verify_identity()` numerical sampling fallback now returns `BLOCKED` with `is_equivalent: false` instead of `UNKNOWN`. This fail-closed behavior ensures that sampling-only agreement is never mistaken for a verified identity.</Info>

Verify mathematical expressions or equations using SymPy symbolic computation.

**Request:**

```json
{
  "expression": "x**2 + 2*x + 1 = (x+1)**2",
  "context": {
    "domain": "real"
  }
}
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `expression` | string | Yes | Mathematical expression or equation. Use `=` for equations |
| `context` | object | No | Optional context (e.g., `{"domain": "real"}` to restrict to real numbers) |

**Response (equation):**

```json
{
  "status": "VERIFIED",
  "is_valid": true,
  "result": true,
  "left_side": "x**2 + 2*x + 1",
  "right_side": "(x + 1)**2",
  "simplified_difference": "0",
  "agent_message": "Identity is true",
  "proof_ref": "sha256:...",
  "attestation": "eyJ...",
  "admission": "ADMIT"
}
```

Every response from this endpoint includes `admission`. Gate on `admission`, not on `status`: `ADMIT` only when `status` is `VERIFIED` and `is_valid` is `true`. A `VERIFIED` response also carries `proof_ref` and its signed `attestation`.

| Outcome | Example | `status` | `is_valid` | `admission` |
|---------|---------|----------|------------|-------------|
| Proven true | `2 + 2 = 4` | `VERIFIED` | `true` | `ADMIT` |
| Proven false | `2 + 2 = 5` | `VERIFIED` | `false` | `BLOCKED` |
| Undecided symbolic difference | SymPy can't decide the difference is zero or non-zero | `UNVERIFIABLE` | `false` | `BLOCKED` |
| Domain-restricted identity | `x/x = 1`, `(x**2-1)/(x-1) = x+1` | `UNVERIFIABLE` | `false` | `BLOCKED` |

**Response (proven false):**

```json
{
  "status": "VERIFIED",
  "is_valid": false,
  "result": false,
  "left_side": "4",
  "right_side": "5",
  "simplified_difference": "-1",
  "agent_message": "Identity is false",
  "proof_ref": "sha256:...",
  "attestation": "eyJ...",
  "admission": "BLOCKED"
}
```

A proven-false identity is a decided verdict, so `status` is `VERIFIED` and `proof_ref` is set. Previous versions returned `UNVERIFIABLE` for it.

**Response (domain-restricted identity):** An identity that holds only after SymPy cancels a removable singularity returns `UNVERIFIABLE` with `constraint_id: "math.domain_restricted_identity"`. For example, `x/x = 1` is false at `x = 0`. See [Domain-restricted identities](/engines/math#domain-restricted-identities).

The audit log row's `is_verified` follows `is_valid`, so a proven-false identity is logged as not verified.

**Response (expression):**

```json
{
  "status": "VERIFIED",
  "is_valid": true,
  "value": 4.0,
  "exact_value": "4",
  "simplified": "4",
  "original": "2 + 2",
  "agent_message": "Expression evaluated",
  "proof_ref": "sha256:...",
  "attestation": "eyJ...",
  "admission": "ADMIT"
}
```

Symbolic expressions that cannot be evaluated to a numeric value include `is_symbolic: true`. Expressions involving complex numbers include `is_complex: true`.

**Ambiguous expressions:** Expressions with implicit multiplication after division (e.g., `1/2(3+1)`) are rejected with `is_valid: false`, `result: false`, `status: "BLOCKED"`, and `admission: "BLOCKED"`. The response includes `warning: "ambiguous"` and an `agent_message` explaining why. Rewrite the expression with explicit parentheses or a `*` operator to remove the ambiguity.

```json
{
  "is_valid": false,
  "result": false,
  "status": "BLOCKED",
  "warning": "ambiguous",
  "agent_message": "Expression may be ambiguous due to implicit multiplication after division",
  "simplified": "...",
  "admission": "BLOCKED"
}
```

**Error cases:** Division by zero, `log(0)`, and square root of negative numbers in the real domain return `status: "BLOCKED"`, `is_valid: false`, and `admission: "BLOCKED"`, with a descriptive `error` and `agent_message`.

**Tolerance bounding:** This endpoint takes no `tolerance`. The bound applies to the engine method `VerificationEngine.verify_math(expression, expected, tolerance)`, which returns an engine dictionary without `admission`. When it verifies an expression against an expected value with a `tolerance` parameter, the engine enforces a deterministic upper bound on the tolerance. The maximum allowed tolerance is `max(0.01, abs(calculated_value) * 0.01)`. If the requested tolerance exceeds this bound, the request returns a `BLOCKED` status. Invalid tolerance values (negative, `NaN`, `Infinity`, or non-numeric) are also rejected with `BLOCKED`.

**Engine dictionary (tolerance exceeded):**

```json
{
  "is_correct": false,
  "error": "Tolerance exceeds deterministic verification bound",
  "requested_tolerance": "1000",
  "max_allowed_tolerance": "0.02000000",
  "calculated_value": "2.000000",
  "precision_mode": "decimal",
  "status": "BLOCKED"
}
```

| Field | Type | Description |
|-------|------|-------------|
| `requested_tolerance` | string | The tolerance value that was submitted |
| `max_allowed_tolerance` | string | The maximum tolerance the engine allows for the computed result |
| `calculated_value` | string | The engine's computed result |
| `precision_mode` | string | `"decimal"` or `"float"` depending on the computation path |

### POST /verify/logic

Verify logical constraints. Routes through the QWED Control Plane.

**Request:**

```json
{
  "query": "Is there an x greater than 5 and less than 10?",
  "provider": "openai"
}
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `query` | string | Yes | A logic question in natural language. The server translates it into the [QWED DSL](/api/dsl-reference) with the LLM provider and checks the DSL with Z3. It does not check DSL directly. |
| `provider` | string | No | Preferred LLM provider |

**Response:**

```json
{
  "status": "SAT",
  "model": {"x": "6", "y": "9"},
  "provider_used": "openai_compat"
}
```

The `provider_used` field indicates which LLM provider handled the translation step. This field is included in both success and error responses, which helps with debugging provider routing issues.

| Status | Meaning |
|--------|---------|
| `SAT` | Satisfiable — a solution exists |
| `UNSAT` | Unsatisfiable — no solution possible |
| `BLOCKED` | Request blocked by security policy (returns HTTP 403) |
| `ERROR` | Internal verification error |

**Error response:**

```json
{
  "status": "ERROR",
  "error": "Internal verification error",
  "provider_used": "openai_compat"
}
```

The provider translation step runs under `QWED_PROVIDER_TIMEOUT` (default 30 seconds) and the Z3 solve under `QWED_Z3_TIMEOUT` (default 15 seconds). A timeout returns the `ERROR` response above.

### POST /verify/code

<Info>Updated in v7.0.0 (breaking)</Info>

Check code for security vulnerabilities using AST analysis. Returns the unified [`DiagnosticResult`](/advanced/diagnostics) shape plus a separate `admission` decision.

**Request:**

```json
{
  "code": "import os\nos.system('rm -rf /')",
  "language": "python"
}
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `code` | string | Yes | Source code to analyze |
| `language` | string | No | Programming language (default: `python`) |

**Response (unsafe code — proven unsafe, not admitted):**

```json
{
  "status": "VERIFIED",
  "agent_message": "The code failed security verification and is not safe to use.",
  "developer_fields": {
    "constraint_id": "code_verifier.code_unsafe",
    "is_safe": false,
    "is_valid": false,
    "language": "python",
    "critical_count": 1,
    "issues": [
      {
        "severity": "CRITICAL",
        "type": "os.system",
        "line_number": 2,
        "description": "Shell command execution"
      }
    ]
  },
  "proof_ref": "sha256:...",
  "is_authoritative": true,
  "admission": "BLOCKED"
}
```

| Field | Type | Description |
|-------|------|-------------|
| `status` | string | `VERIFIED` when the scan completed (safe **or** unsafe code); `BLOCKED` when verification itself failed (empty code, unsupported language, internal error) |
| `admission` | string | `ADMIT` or `BLOCKED` — the fail-closed admission decision. `ADMIT` only when `status` is `VERIFIED` **and** `developer_fields.is_valid` is `true` |
| `developer_fields.is_valid` | boolean | The safety gate — `true` only when no critical issue was found |
| `developer_fields.issues` | array | Detected vulnerabilities with severity, type, line number, and description |
| `proof_ref` | string | Present on `VERIFIED` results (including verified-unsafe); `null` on `BLOCKED` |

<Warning>
**Breaking change (v7.0.0):** proven-unsafe code now returns HTTP 200 with `status: "VERIFIED"` (previously `BLOCKED`). `VERIFIED` answers "was the code checked?", not "is it safe to execute?". Consumers that gated on `status` for safety must switch to the `admission` field or `developer_fields.is_valid`.
</Warning>

| Status | Description |
|--------|-------------|
| 503 | `Code verification timed out.` The scan exceeded `QWED_CODE_VERIFY_TIMEOUT` (default 10 seconds) |

### POST /verify/sql

<Info>Updated in v7.0.0 (breaking)</Info>

Validate SQL queries against a provided schema. Returns the unified [`DiagnosticResult`](/advanced/diagnostics) shape plus a separate `admission` decision.

**Request:**

```json
{
  "query": "SELECT * FROM users WHERE id = 1",
  "schema_ddl": "CREATE TABLE users (id INT, name TEXT)",
  "dialect": "sqlite"
}
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `query` | string | Yes | SQL query to validate |
| `schema_ddl` | string | Yes | DDL schema definition (e.g., `CREATE TABLE` statements) |
| `dialect` | string | No | SQL dialect (default: `sqlite`) |

**Response (safe query):**

```json
{
  "status": "VERIFIED",
  "agent_message": "The SQL query passed verification and is safe to execute.",
  "developer_fields": {
    "constraint_id": "sql_verifier.sql_valid",
    "is_valid": true,
    "malicious_classification": false
  },
  "proof_ref": "sha256:...",
  "is_authoritative": true,
  "admission": "ADMIT"
}
```

A proven-malicious query returns `status: "VERIFIED"` with `developer_fields.is_valid: false`, `developer_fields.malicious_classification: true`, and `admission: "BLOCKED"` — proving malice is a successful proof, so the truth verdict is preserved while admission is denied. `BLOCKED` status is reserved for verification failures: `sql_verifier.parse_error`, `sql_verifier.schema_parse_error`, `sql_verifier.complexity_limit_exceeded`, and `sql_verifier.execution_error`. See the [SQL engine](/engines/sql) page for the full contract.

### POST /verify/consensus

<Info>New in v4.0.0 · Updated in v5.0.0</Info>

Multi-engine consensus verification. Runs the query through multiple verification engines and requires agreement above a confidence threshold. This endpoint is rate-limited per API key.

Mathematical expressions are parsed and compared using `Decimal` arithmetic internally, which avoids floating-point drift when engines cross-check results.

<Note>The fact engine is excluded from automatic engine selection during consensus verification. Fact-based verification requires external context and will return an error if invoked without it, preventing self-referential consensus loops.</Note>

**Request:**

```json
{
  "query": "The square root of 144 is 12",
  "verification_mode": "high",
  "min_confidence": 0.95
}
```

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| `query` | string | Yes | — | The claim to verify |
| `verification_mode` | string | No | `single` | `single`, `high`, or `maximum` |
| `min_confidence` | float | No | `0.95` | Minimum confidence threshold, 0–1 |

**Verification modes:**

| Mode | Engines | Use case |
|------|---------|----------|
| `single` | 1 | Fast, single engine verification |
| `high` | 2 | Higher confidence for important claims |
| `maximum` | 3+ | Critical domains (medical, financial) |

**Response:**

```json
{
  "final_answer": "12",
  "confidence": 98.5,
  "engines_used": 2,
  "agreement_status": "UNANIMOUS",
  "verification_chain": [
    {
      "engine": "math",
      "method": "symbolic",
      "result": "12",
      "confidence": 99.0,
      "latency_ms": 12.5,
      "success": true,
      "status": "VERIFIED"
    }
  ],
  "total_latency_ms": 45.2,
  "meets_requirement": true
}
```

| Field | Type | Description |
|-------|------|-------------|
| `confidence` | float | Confidence as a percentage (0–100) |
| `verification_chain` | array | Detailed results from each engine |
| `verification_chain[].status` | string | Trust-boundary status from that engine — `VERIFIED`, `UNVERIFIABLE`, or `BLOCKED` |
| `meets_requirement` | boolean | True only when consensus is `VERIFIED` at the trust boundary **and** `confidence` meets `min_confidence`. Confidence alone is never sufficient. |

<Note>
Only unanimous `VERIFIED` engine outcomes can produce a `VERIFIED` consensus. Advisory-only sub-engines (statistical computation, code execution) always return `UNVERIFIABLE`, so a query answered solely by those paths never satisfies `meets_requirement`. See the [Consensus engine](/engines/consensus#sub-engine-status-contract) page for the full sub-engine contract.
</Note>

| Status | Description |
|--------|-------------|
| 400 | Invalid verification mode |
| 422 | Consensus confidence below the requested `min_confidence` threshold |
| 503 | Secure Docker sandbox unavailable — required for Python engine in `high`/`maximum` mode |

Each server process runs at most `QWED_SANDBOX_MAX_CONCURRENT` sandbox containers at once (default 4). If a Python engine run can't get a sandbox slot within `QWED_SANDBOX_ACQUIRE_TIMEOUT` (default 10 seconds), QWED rejects the run with `Sandbox capacity reached — retry shortly.` instead of starting another container. A capacity rejection never produces a `VERIFIED` result.

### POST /verify/image

Verify claims about image content. Accepts multipart form data with an image file (max 10 MB). Supported formats: PNG, JPEG, GIF, WebP.

**Request:**

```bash
curl -X POST http://localhost:8000/verify/image \
  -H "X-API-Key: qwed_your_key" \
  -F "image=@photo.jpg" \
  -F "claim=The image is 800x600 pixels"
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `image` | file | Yes | Image file (max 10 MB; PNG, JPEG, GIF, WebP) |
| `claim` | string | Yes | The claim about the image to verify |

**Response:**

```json
{
  "verdict": "SUPPORTED",
  "confidence": 0.95,
  "reasoning": "Image dimensions match the claimed resolution",
  "methods_used": ["metadata_analysis", "pixel_inspection"]
}
```

| Verdict | Meaning |
|---------|---------|
| `SUPPORTED` | Claim is confirmed by image analysis |
| `REFUTED` | Claim contradicts image analysis |
| `INCONCLUSIVE` | Cannot determine from available methods |
| `VLM_REQUIRED` | Visual Language Model needed for deeper analysis |

### POST /verify/stats

Verify statistical claims against CSV data. Accepts multipart form data with a CSV file.

Statistical code execution requires the secure Docker sandbox. If Docker is unavailable, the endpoint returns HTTP 503. If the verification is blocked by a security policy, it returns HTTP 403.

**Request:**

```bash
curl -X POST http://localhost:8000/verify/stats \
  -H "X-API-Key: qwed_your_key" \
  -F "file=@data.csv" \
  -F "query=The average salary is above 50000"
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `file` | file | Yes | CSV data file |

### POST /verify/batch

Verify multiple items in a single request. Processes all items concurrently and returns aggregated results. Maximum 100 items per batch.

**Request:**

```json
{
  "items": [
    {"query": "What is 2+2?", "type": "natural_language"},
    {"query": "(AND (GT x 5) (LT y 10))", "type": "logic"},
    {"query": "x**2 + 2*x + 1 = (x+1)**2", "type": "math"}
  ]
}
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `items` | array | Yes | Array of verification items (max 100) |
| `items[].query` | string | Yes | The claim to verify |
| `items[].type` | string | No | Verification type: `natural_language`, `logic`, `math`, `code`, `fact`, `sql` (default: `natural_language`) |
| `items[].params` | object | No | Additional parameters for the verification |

**Response:**

Each entry in `items` is a per-item response. For math items the verdict is the [`DiagnosticResult`](/advanced/diagnostics) record nested under the item's `result` — the same three-layer verdict shape used by `POST /verify/math` — so batch and single-item math verifications share one contract:

- `result.status` — `VERIFIED`, `UNVERIFIABLE`, or `BLOCKED`.
- `result.agent_message` — short human-readable summary safe to surface to the caller.
- `result.developer_fields` — engine detail (including the legacy `is_valid` flag for backward compatibility).
- `result.proof_ref` — cryptographic hash of the retained proof artifact. Present only when `result.status == VERIFIED`; `null` otherwise. **This is the authority bit** — downstream gates must reject any item whose `proof_ref` is `null`.
- `result.admission` — `ADMIT` or `BLOCKED` on math, SQL, and code items, the same decision `POST /verify/math`, `POST /verify/sql`, and `POST /verify/code` return. Natural-language items always carry `BLOCKED`. Logic and fact items carry no admission. Admit an item only when `admission` is `ADMIT`, `status` is `VERIFIED`, and `proof_ref` is set. A proven-malicious query or proven-unsafe code is `VERIFIED` with admission `BLOCKED`. A math item whose sides differ is `UNVERIFIABLE` with admission `BLOCKED` (see the table below), unlike `POST /verify/math`, which returns a proven-false identity as `VERIFIED`.

QWED stores each math and SQL item's admission in its audit row, so `/audit/logs` shows it. Rows written before this change keep `admission: null`.

A SQL item must include `params.schema_ddl`. An item without it is marked `failed` with the error `Missing 'schema_ddl'`, the same message `POST /verify/sql` returns, and carries no admission.

```json
{
  "job_id": "batch_abc123",
  "status": "completed",
  "progress_percent": 100.0,
  "total_items": 2,
  "completed_items": 2,
  "failed_items": 0,
  "items": [
    {
      "id": "batch_abc123-0",
      "query": "x**2 + 2*x + 1 = (x+1)**2",
      "type": "math",
      "status": "completed",
      "result": {
        "status": "VERIFIED",
        "agent_message": "Identity verified",
        "developer_fields": {
          "query": "x**2 + 2*x + 1 = (x+1)**2",
          "type": "math",
          "is_valid": true,
          "diff": "0"
        },
        "proof_ref": "sha256:9f2c…",
        "admission": "ADMIT",
        "is_authoritative": true
      },
      "latency_ms": 12.3
    },
    {
      "id": "batch_abc123-1",
      "query": "x + x",
      "type": "math",
      "status": "completed",
      "result": {
        "status": "UNVERIFIABLE",
        "agent_message": "Expression simplified, but no equality or proof claim was provided",
        "developer_fields": {
          "query": "x + x",
          "type": "math",
          "is_valid": false,
          "simplified": "2*x"
        },
        "proof_ref": null,
        "admission": "BLOCKED",
        "is_authoritative": false
      },
      "latency_ms": 8.1
    }
  ]
}
```

#### Math items: proof vs. simplification

Math items are routed through the trust boundary (`enforce_trust_decision(require_attestation=True)` on VERIFIED, with a signed attestation issued via `create_verification_attestation`). Three outcomes are possible:

| Result | `status` | `proof_ref` | When |
|--------|----------|-------------|------|
| Verified identity | `VERIFIED` | `sha256:...` | Equality claim (e.g., `x**2 + 2*x + 1 = (x+1)**2`) simplifies to `0` **and** attestation signing succeeds. |
| Not equal | `UNVERIFIABLE` | `null` | Equality claim where the two sides do not simplify to the same expression. `developer_fields.is_valid` is `false` and `developer_fields.diff` shows the non-zero difference. |
| Simplification only | `UNVERIFIABLE` | `null` | Expression without an equality (e.g., `x + x`). `developer_fields.simplified` contains the simplified form. |
| Domain-restricted identity | `UNVERIFIABLE` | `null` | Equality whose sides are undefined at different points, such as `x/x = 1`. `constraint_id` is `math.domain_restricted_identity`, as on `POST /verify/math`. |

If attestation signing fails on an otherwise-verified identity, the item is downgraded to `UNVERIFIABLE` with `developer_fields.constraint_id = "api.attestation.signing_error"` — a math result is never returned as `VERIFIED` without a signed proof.

<Warning>
Bare expressions (no `=`) always return `UNVERIFIABLE`. A successful symbolic simplification is not a verified claim. To get a `VERIFIED` outcome from a math item, submit an equality (e.g., `x + x = 2*x`).
</Warning>

<Info>
The pre-v6.0 top-level `is_valid` field is preserved inside `developer_fields.is_valid` for backward compatibility, but new code should gate on `result.status == "VERIFIED"` and the presence of `result.proof_ref`. The batch response does not include a pass/fail aggregate because a boolean cannot represent the three-status verdict — count `items[].result.status == "VERIFIED"` entries directly if you need a success ratio.
</Info>

Each item runs under `QWED_BATCH_ITEM_TIMEOUT` (default 60 seconds). An item that times out is marked `failed` with its error recorded, and the rest of the job still completes.

**Audit trail:** QWED appends one signed, hash-chained audit row per item, including failed items. Each row stores the item's query and a result with `batch_job_id`, `batch_item_id`, `batch_item_type`, `item_status`, and `details` (the item's `result` or `error`). The row's domain and `is_verified` follow the rule of the item type's own `/verify/*` route. If the audit append for an item fails, QWED marks that item `failed`, returns `"result": null` with `"error": "audit persistence failed"`, and counts it in `failed_items`. No item result is returned without its audit row.

| Status | Description |
|--------|-------------|
| 400 | No items, or more than 100 items |
| 503 | `Batch capacity reached — retry shortly.` The job store is full of active jobs. See [Availability limits](/advanced/self-hosting#availability-limits) |

## Verification Context endpoints

<Info>New in v7.1.0</Info>

These endpoints work with [Verification Context](/specs/verification-context) documents, the standardized JSON record of a verification. All three require an API key and are rate-limited per key.

The server signs every document it issues. `from-diagnostic` returns a [v1.1 document](/specs/verification-context#version-1-1-and-the-issuer-attestation) whose `attestation` field is the server's ES256 signature over every other field. By default, `validate` and `resolve` check that signature before they answer, so a document someone else built or edited is refused even when its `proof_ref` resolves.

### POST /verification-context/from-diagnostic

Convert a [`DiagnosticResult`](/advanced/diagnostics) into a schema-valid Verification Context document. Use this when you have an engine verdict and need the standardized VC record for auditing or downstream gating.

**Request:**

```json
{
  "query": "x**2 + 2*x + 1 = (x+1)**2",
  "verifier": "MathVerifier",
  "diagnostic": {
    "status": "VERIFIED",
    "agent_message": "Identity verified",
    "developer_fields": {"is_valid": true},
    "proof_ref": "sha256:9f2c…"
  },
  "verifier_version": "7.1.0",
  "attestation_token": "<ES256 JWT attestation>"
}
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `query` | string | Yes | The formal statement that was verified |
| `verifier` | string | Yes | Name of the engine that produced the diagnostic |
| `diagnostic` | object | Yes | The `DiagnosticResult` record (`status` / `agent_message` / `developer_fields` / `proof_ref`) |
| `verifier_version` | string | No | Engine version. Defaults to the installed `qwed` package version |
| `attestation_token` | string | No | Signed attestation for the diagnostic. Required to keep a `VERIFIED` status |

**Response:** a v1.1 Verification Context document (`spec_version`, `object`, `context`, `verdict`, `attestation`), signed by the server.

**Fail-closed behavior:**

- A malformed `diagnostic` payload is converted to a `BLOCKED` document instead of being rejected, so the audit trail records the failure.
- A `VERIFIED` diagnostic without an `attestation_token` fails closed to `BLOCKED` (`trust_gate.mandatory_attestation_missing`). A supplied invalid token fails closed to `BLOCKED` (`trust_gate.invalid_attestation_token`). A valid token with mismatched claims uses the corresponding `trust_gate.claims_*` code. Attestation is enforced through the same trust boundary as `/verify/*`.
- The server records the diagnostic but does not vouch for it. The caller's `agent_message` and `developer_fields` are kept under `developer_fields.caller_supplied` and decide nothing, `is_valid` included.
- The admission is `DENY` unless `attestation_token` also signs `ADMIT` for this verdict (`qwed.admission`), as the token of an answer the server admitted does. An admitted document names the engine that signed the token, and this server's version, as its verifier. Your `verifier` and `verifier_version` are kept under `caller_supplied`.

| Status | Description |
|--------|-------------|
| 422 | The resulting document failed Verification Context validation, or the canonical encoding refuses it (for example, a lone surrogate in a string) |
| 500 | Audit persistence, or attestation verification or signing, failed |

### POST /verification-context/validate

Validate a Verification Context document against the JSON Schema of its `spec_version` (v1.0 or v1.1), including the verdict/`proof_ref` invariants. By default, the server first checks the document's attestation with its own signing key.

**Request:**

```json
{
  "document": {
    "spec_version": "1.1",
    "object": {"formal_statement": "x**2 + 2*x + 1 = (x+1)**2"},
    "context": {
      "interpretation": {"theory": "real-closed field", "logic": "first-order logic"},
      "proof": {"verifier": "qwed", "verifier_version": "7.1.0"},
      "evidence": {"evidence": {"status": "VERIFIED"}, "proof_ref": "sha256:9f2c…"},
      "decision": {"admission": "ADMIT"}
    },
    "verdict": "VERIFIED",
    "attestation": "<ES256 JWT from from-diagnostic>"
  }
}
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `document` | object | Yes | The Verification Context document |
| `require_attestation` | boolean | No | Default `true`. The document must carry an `attestation` that the server's key verifies and that signs this document. Set `false` to check the schema alone, for example for a v1.0 document |

**Response:**

```json
{"valid": true}
```

A document that fails the attestation check or validation returns HTTP 200 with `valid: false` and an `error`. Gate on the `valid` field. A server-side failure is a `500` instead (see the status table below), so treat any non-200 response as not validated.

| `error` | Cause |
|---------|-------|
| `attestation_required` | The document carries no `attestation` |
| `attestation_invalid` | The attestation does not verify with the server's key, or does not sign this document (it was edited after signing, or carries another document's token) |
| `validation_failed` | Schema or invariant violation |

<Warning>
**Behavior change.** A v1.0 document has no `attestation`, so it now returns `attestation_required` unless you send `"require_attestation": false`. Older SDK versions don't send the flag.
</Warning>

| Status | Description |
|--------|-------------|
| 500 | Audit persistence failed, or the server could not load its signing key to check the attestation |

### POST /verification-context/resolve

Resolve the `proof_ref` evidence commitment of a Verification Context document. The server removes the stored `proof_ref`, re-derives the SHA-256 commitment over the canonical (RFC 8785) bound payload, and compares it to the stored value.

A `proof_ref` is an unkeyed commitment: anyone can compute one for a document they built. So, by default, the server first checks the document's attestation, as for `/validate`, and takes the same `require_attestation` parameter.

**Request:**

```json
{
  "document": {
    "spec_version": "1.1",
    "object": {"formal_statement": "x**2 + 2*x + 1 = (x+1)**2"},
    "context": {
      "interpretation": {"theory": "real-closed field", "logic": "first-order logic"},
      "proof": {"verifier": "qwed", "verifier_version": "7.1.0"},
      "evidence": {"evidence": {"status": "VERIFIED"}, "proof_ref": "sha256:9f2c…"},
      "decision": {"admission": "ADMIT"}
    },
    "verdict": "VERIFIED",
    "attestation": "<ES256 JWT from from-diagnostic>"
  }
}
```

**Response:**

```json
{"resolved": true}
```

`resolved` is `true` only when the attestation verifies (unless `require_attestation` is `false`), the document has `verdict: "VERIFIED"`, it validates against the schema, and the stored `proof_ref` matches the re-derived commitment. An attestation failure returns `{"resolved": false, "error": "attestation_required"}` or `"attestation_invalid"`. Any other failure (non-`VERIFIED` verdict, schema failure, mismatched or missing commitment) returns `{"resolved": false}`. A `proof_ref` that cannot be resolved confers no authority.

## Admin endpoints

<Info>New in v4.0.0</Info>

Admin endpoints authenticate your API key with the `X-API-Key` header, then authorize the request by the role of the user who owns the key. Every admin endpoint acts only on your own organization, which is the organization the API key belongs to.

Before QWED checks the role, the request must meet all of these conditions. Otherwise QWED returns `403 Forbidden`:

- The API key is active, not revoked, and not expired.
- The key's owning user is active and belongs to the key's organization.
- The organization is active.

| Endpoint | Allowed roles | Another organization's ID |
|----------|---------------|---------------------------|
| `GET /admin/compliance/export/csv` | `owner`, `admin` | `403 Forbidden` |
| `GET /admin/compliance/verify/{log_id}` | `owner`, `admin` | `404 Not Found` |
| `GET /admin/compliance/verify-trail` | `owner`, `admin` | Not applicable (always your organization) |
| `GET /admin/compliance/report/soc2/{org_id}` | `owner`, `admin` | `403 Forbidden` |
| `GET /admin/security/threats/{org_id}` | `owner`, `admin` | `403 Forbidden` |
| `POST /admin/keys/rotate` | `owner`, `admin`, `member` | `404 Not Found` |

A caller whose role isn't allowed gets `403 Forbidden` with `"Insufficient permissions for this operation"`. A missing or invalid API key returns `401 Unauthorized`.

The JWT-authenticated `/auth/api-keys` and `/audit` routes use the same role ranking. See [Roles on API-key and audit routes](/api/authentication#roles-on-api-key-and-audit-routes).

### Session sign-in for compliance endpoints

The four `/admin/compliance/*` endpoints also accept a signed-in session, so a dashboard user doesn't need to paste an API key into the browser. Send the `access_token` from [`POST /auth/signin`](/api/authentication) as a bearer token:

```text
Authorization: Bearer <jwt_token>
```

- The token must be valid and its user must exist. Otherwise QWED returns `401 Unauthorized`.
- The user must be active, belong to an active organization, and hold the `owner` or `admin` role. Otherwise QWED returns `403 Forbidden`.
- If you send both `X-API-Key` and a bearer token, QWED uses the API key.
- The session's organization is the signed-in user's organization. Organization scoping works the same as with an API key.

Other admin endpoints (`/admin/security/threats/{org_id}` and `/admin/keys/rotate`) accept only an API key. A bearer token alone returns `401 Unauthorized`.

<Note>
Before this change, every admin endpoint returned `401 Unauthorized`, even for valid owner and admin keys. Admin endpoints now authorize by role and are scoped to the caller's organization.
</Note>

### GET /admin/compliance/export/csv

Export your organization's audit trail as a CSV file (`text/csv`).

The `Chain Status` column reports `Chained` when a row carries a hash and `Legacy` when it was written before the API used the hash chain. `Chained` doesn't mean the row was verified. Use [`GET /admin/compliance/verify/{log_id}`](#get-admin-compliance-verify-log-id) to verify it.

| Parameter | Type | Description |
|-----------|------|-------------|
| `organization_id` | integer (query) | Must be your own organization ID |

Passing another organization's ID returns `403 Forbidden` with `"Cannot access another organization's data"`.

```bash
curl --fail-with-body -H "X-API-Key: qwed_live_your_admin_key" \
  "http://localhost:8000/admin/compliance/export/csv?organization_id=12"
```

### GET /admin/compliance/verify/{log_id}

Cryptographically verify a specific audit log entry using HMAC-SHA256 and hash-chain validation.

The entry must belong to your organization. QWED returns `404 Not Found` for a log ID in another organization, so the response doesn't reveal whether that entry exists.

The response reports three independent checks: payload hash, HMAC signature (compared in constant time), and chain linkage to the prior entry within the same organization. Genesis entries must have a `null` `previous_hash`; non-genesis entries must link to a non-empty prior entry hash. Entries with malformed stored result payloads cause verification to fail closed with `SecurityError` instead of returning `"valid": true`.

Hash matching accepts either the current canonical payload (which includes `raw_llm_output`) or the legacy canonical payload, so entries written before that field was covered remain verifiable after the upgrade.

**Response:**

```json
{
  "valid": true,
  "legacy": false,
  "checks": {
    "hash_valid": true,
    "signature_valid": true,
    "chain_valid": true
  },
  "errors": [],
  "log_id": 42,
  "timestamp": "2026-03-20T12:00:00Z"
}
```

**Legacy entries.** Rows written before the API used the hash chain have no hash or signature. For an unchained row with no chained row before it, the response sets `"legacy": true` and `"valid": false`, with all three checks `false`:

```json
{
  "valid": false,
  "legacy": true,
  "checks": {
    "hash_valid": false,
    "signature_valid": false,
    "chain_valid": false
  },
  "errors": ["Entry predates the audit chain (no hash or signature); it cannot be verified"],
  "log_id": 7,
  "timestamp": "2026-10-01T09:00:00+00:00"
}
```

An unchained row after a chained row is not legacy. It fails verification. See [Legacy entries](/advanced/compliance#legacy-entries).

<Note>
`AuditLogger` requires `QWED_AUDIT_SECRET_KEY` to be set, and the server refuses to start without it. If the key is missing or persisted chain continuity cannot be loaded, initialization raises `SecurityError` and verification endpoints fail closed. Every `/verify/*` endpoint (one row per item for `/verify/batch`), the Verification Context routes, `POST /agents/{agent_id}/verify`, and `POST /audit/seed` write their audit row through the signed chain. If that write fails, the request returns `500` with `audit persistence failed`.
</Note>

### POST /audit/seed

Write 10 sample audit rows for your organization through the signed hash chain. Use this only in development. Each row is marked `{"sample": true}` in its result and timestamped when written.

The route is disabled by default. Set `QWED_ENABLE_AUDIT_SEED=1` on the server to enable it.

| Status | Description |
|--------|-------------|
| 404 | Sample seeding is disabled (`QWED_ENABLE_AUDIT_SEED` is not `1`). No rows are written |
| 500 | Audit persistence failed |

### GET /admin/compliance/report/soc2/{org_id}

Return a security activity summary for your organization over the last 90 days. `org_id` must be your own organization ID. Another organization's ID returns `403 Forbidden`.

QWED computes every value from its own records. The response has `report_type` `"Security activity summary"`, `report_version` `"2.0"`, and a `disclaimer` stating that it is not a SOC 2 report or an auditor's attestation. The path keeps `soc2` for compatibility.

- `metrics` counts verifications, security events (`security_events_by_type` groups them by recorded event type), active users, and active API keys.
- `audit_trail` checks the signature and hash chain of every audit entry in the period. `status` is `VERIFIED` (with `evidence` and a `sha256:` `proof_ref`), `NO_ENTRIES`, or `NOT_VERIFIED`. The check fails closed: any failed or legacy entry, or a check that can't run (for example, `QWED_AUDIT_SECRET_KEY` unset), returns `NOT_VERIFIED`.

```bash
curl --fail-with-body -H "X-API-Key: qwed_live_your_key" \
  "http://localhost:8000/admin/compliance/report/soc2/1"
```

`audit_trail.first_failed_entry_id` is the lowest entry ID that failed its signature or chain check, or `null` when none failed or the check couldn't run.

See [Security activity summary](/advanced/compliance#1-security-activity-summary) for the full response and field reference.

### GET /admin/compliance/verify-trail

Check the signature and hash chain of every audit entry in your organization over a period. Use it to confirm the chain is intact up to a given entry, instead of calling `GET /admin/compliance/verify/{log_id}` once per entry. Owners and admins can call it with an API key or a signed-in session.

| Parameter | Type | Description |
|-----------|------|-------------|
| `start` | ISO 8601 datetime (query, optional) | Start of the period. Omit for no lower bound. |
| `end` | ISO 8601 datetime (query, optional) | End of the period. Omit for no upper bound. |

With neither parameter, QWED checks the whole chain. QWED reads a time without a zone as UTC and converts any other offset to UTC. A `start` later than `end` returns `400 Bad Request`.

```bash
curl --fail-with-body -H "Authorization: Bearer $QWED_SESSION_TOKEN" \
  "http://localhost:8000/admin/compliance/verify-trail?start=2026-10-01T00:00:00Z"
```

**Response:**

```json
{
  "organization_id": 1,
  "start": "2026-10-01T00:00:00+00:00",
  "end": null,
  "status": "NOT_VERIFIED",
  "proof_ref": null,
  "evidence": null,
  "scope": "Signature and hash-chain check of the audit entries recorded in the period. It does not show that every request was recorded.",
  "total_entries": 240,
  "verified_entries": 238,
  "failed_entries": 2,
  "legacy_entries": 0,
  "first_failed_entry_id": 1187,
  "errors": ["..."],
  "total_errors": 2,
  "errors_truncated": false
}
```

The fields after `end` match `audit_trail` in the [security activity summary](/advanced/compliance#audit-trail-status). `status` is `VERIFIED` (with `evidence` and a `sha256:` `proof_ref`) only when the period has entries and all pass. `NO_ENTRIES` means the period has none. `NOT_VERIFIED` means any entry failed, any entry is a legacy entry, or the check couldn't run. `first_failed_entry_id` names the lowest entry ID that failed, or is `null`.

### GET /admin/security/threats/{org_id}

Returns a real-time threat summary for your organization, including blocked injection attempts and anomalous patterns. `org_id` must be your own organization ID. Another organization's ID returns `403 Forbidden`.

### POST /admin/keys/rotate

Rotate an API key and return the new secret once. Owners, admins, and members can call this endpoint, subject to these rules:

- **Your own key:** any allowed role can rotate a key it owns.
- **Another user's key:** only an `owner` or `admin` can rotate it, and only when the key's owner doesn't hold a higher role. An admin can't rotate an owner's key. A member can't rotate anyone else's key. These cases return `403 Forbidden`.
- **Organization scope:** the key must belong to your organization. A key ID in another organization returns `404 Not Found`, without revealing that the key exists.
- **Live keys only:** QWED treats a revoked or inactive key as absent and returns `404 Not Found`. You can't rotate a dead credential into a new working secret.
- **Atomic:** QWED revokes the old key and mints the replacement in one transaction. Concurrent rotations of the same key produce exactly one replacement. The others return `404 Not Found`.

| Parameter | Type | Description |
|-----------|------|-------------|
| `key_id` | integer (query) | ID of the key to rotate |

```bash
curl --fail-with-body -X POST -H "X-API-Key: qwed_live_your_key" \
  "http://localhost:8000/admin/keys/rotate?key_id=42"
```

**Response:**

```json
{
  "status": "rotated",
  "old_key_id": 42,
  "new_key_id": 57,
  "new_key_preview": "qwed_live_ab...",
  "new_key_secret": "qwed_live_..."
}
```

Store `new_key_secret` immediately. QWED returns it only in this response.

## Webhook endpoints

### POST /webhooks/secret-scanning

Receive signed secret-leak notifications from GitHub secret scanning (or any GitHub-compatible partner scanner). The endpoint is the intake side of the leaked-QWED-key revocation pipeline: authenticated reports of leaked tokens are handed to the revocation sink after signature verification succeeds.

The endpoint is **intentionally unauthenticated** — it must be reachable by external scanners that have no QWED credentials. The ECDSA signature over the raw request body is the only credential; nothing in the payload is parsed, logged, or persisted until the signature is verified against GitHub's published public keys.

**Request headers:**

| Header | Required | Description |
|--------|----------|-------------|
| `Github-Public-Key-Identifier` | Yes | Key identifier (`key_identifier`) of the signing key from `https://api.github.com/meta/public_keys/secret_scanning` |
| `Github-Public-Key-Signature` | Yes | Base64-encoded ASN.1/DER ECDSA-NIST-P256V1-SHA256 signature over the raw request body |

**Request body:**

A non-empty JSON array of match objects. Extra fields on each item are ignored so scanners can add informational fields over time.

```json
[
  {
    "token": "qwed_live_KEY",
    "type": "qwed_live_api_key",
    "url": "https://github.com/acme-corp/billing-api/blob/main/config.py",
    "source": "commit"
  }
]
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `token` | string | Yes | The leaked token (1–512 characters). Never logged. |
| `type` | string | Yes | Scanner-declared token type (1–128 characters) |
| `url` | string | No | Location where the token was found (max 4096 characters) |
| `source` | string | No | Scanner-declared source (max 64 characters). Defaults to `"unknown"` |

**Envelope caps:**

- Request body: 1 MiB. The stream is bounded incrementally — an over-cap body is rejected the moment the cap is exceeded and never fully buffered.
- Matches per request: 500.
- Signature header: 1024 characters before base64 decode.

**Response (200):**

```json
{"received": 3}
```

A 200 acknowledges a **verified receipt**, not that downstream revocation has finished. Verified matches are handed to a background sink after the response is sent.

**Background handling of verified matches:**

- **Active key:** revoked immediately (`is_active=False`, `revoked_at` set). QWED writes a `SECRET_LEAK_AUTO_REVOKED` security event that carries only the `key_preview`, never the token.
- **Owner email:** sent to the key's user, or to the organization's first active owner or admin as a fallback. SMTP has a 10-second timeout. A failed notification never rolls back the revocation.
- **Already-revoked key or unknown token:** no revocation or owner notification. Redeliveries are idempotent and never send a second email. When false-positive feedback is enabled (next bullet), QWED still reports a label for the match — for an unknown token, `false_positive`.
- **Test keys:** registered scanner patterns cover `qwed_live_` keys only, so `qwed_test_` keys are not reported. The revocation sink itself does not filter by prefix.
- **False-positive feedback (opt-in):** when `QWED_LEAK_FEEDBACK_ENABLED=true`, QWED sends a `true_positive` or `false_positive` label per match to `QWED_LEAK_FEEDBACK_URL` after the revocation attempt. Items carry SHA-256 token hashes unless `QWED_LEAK_FEEDBACK_SEND_RAW=true` is set with an HTTPS URL.

See [Automatic revocation of leaked keys](/advanced/security-hardening#automatic-revocation-of-leaked-keys) and [False-positive feedback reporter](/advanced/security-hardening#false-positive-feedback-reporter) for details.

**Status codes:**

| Status | Meaning |
|--------|---------|
| 200 | Signature verified; matches queued for background handling |
| 400 | Malformed envelope (non-JSON body, wrong shape, or a match object failed validation) |
| 401 | Missing `Github-Public-Key-Identifier` or `Github-Public-Key-Signature` header |
| 403 | Signature invalid, forged, tampered, or signed by an unknown key against a fresh trust anchor |
| 413 | Body exceeds 1 MiB or the batch exceeds 500 matches |
| 503 | Signing-key service unavailable, or the key that signed the request cannot be resolved after a rotation retry — the scanner should redeliver |

All signature-failure responses share a single generic detail (`"invalid webhook signature"`) so the failing verification step is not observable to the caller.

<Note>
Configure your scanner (or a GitHub partner-program registration) to POST to `https://<your-qwed-host>/webhooks/secret-scanning`. No API key or bearer token is provisioned on QWED's side — the signature over the raw body is the sole credential, and QWED fetches the public keys from GitHub on demand. See [Security hardening — Secret-scanning webhook intake](/advanced/security-hardening#6-secret-scanning-webhook-intake) for the trust model and operator configuration.
</Note>
