> **TL;DR:** A QWED result is `VERIFIED` only when a deterministic check produced a proof reference. Where an LLM translates a query into a formal expression (Logic, Consensus, natural-language Math), the deterministic check runs on that translation, which is not itself verified. Anything else a model, sandbox execution or a similarity score contributes is reported as an advisory check and never sets the status. Several engines cannot return `VERIFIED` at all.

---

## The status model

Every engine reports one of three statuses:

| Status | Meaning | `proof_ref` |
|--------|---------|-------------|
| `VERIFIED` | A deterministic check completed and produced a proof reference. | Present |
| `UNVERIFIABLE` | The claim could not be proven: insufficient evidence, ambiguous input, model-only support, a missing provider path or a computation that did not converge. | `null` |
| `BLOCKED` | Verification could not be attempted or was stopped: missing declarations, a parse error, a configuration failure, a security policy violation or a missing dependency. | `null` |

There is no `HEURISTIC` status and no top-level field that labels a result as symbolic or heuristic. The distinction lives in two places:

- `status` and `proof_ref`: only `VERIFIED` carries a proof reference.
- `developer_fields.advisory_checks`: output from LLM fallbacks, NLI labels, vision-model interpretation, heuristic consistency checks and keyword scans. Each entry has `name`, `advisory_only`, `constraint_id` and `details`. Advisory checks never set `status` or `proof_ref`.

`developer_fields.constraint_id` says why a result landed where it did, for example `fact_verifier.heuristic_supported` or `api.math.execution_error`.

A response from the HTTP API has this shape (the entries inside `developer_fields` are also copied to the top level):

```json
{
  "status": "VERIFIED",
  "agent_message": "Expression evaluated",
  "developer_fields": { "is_valid": true, "value": 4.0, "exact_value": "4" },
  "proof_ref": "...",
  "is_authoritative": true
}
```

### Truth and admission are separate

`VERIFIED` means the analysis is authoritative, not that the input is safe or correct. The Code, SQL and Schema engines return `VERIFIED` for a snippet proven unsafe or data proven non-conforming, with `developer_fields.is_valid` set to `false`.

The admission rule turns a result into a decision at a boundary:

| Result | Admission |
|--------|-----------|
| `VERIFIED` and `is_valid` is `true` | `ADMIT` |
| `VERIFIED` and `is_valid` is not `true` | `BLOCKED` |
| `UNVERIFIABLE` or `BLOCKED` | `BLOCKED` |

`POST /verify/code` and `POST /verify/sql` return this decision in an `admission` field, so a safe snippet comes back as `VERIFIED · ADMIT` and a proven-unsafe one as `VERIFIED · BLOCKED`. QWED decides; your integration enforces the decision.

## Engine classification

### Engines that can return `VERIFIED`

| Engine | Endpoint | What decides the result | LLM involvement |
|--------|----------|-------------------------|-----------------|
| **Math** | `POST /verify/math` | SymPy. An identity is `VERIFIED` when the difference simplifies to zero; an expression is `VERIFIED` when it simplifies or evaluates. A false identity is `UNVERIFIABLE`; division by zero or an undefined result is `BLOCKED`. | None |
| **Logic** | `POST /verify/logic` | An LLM translates the query into QWED-DSL, which is validated and compiled to Z3. Satisfiable is `VERIFIED`, unsatisfiable is `UNVERIFIABLE`. | Translation only. The translation itself is not verified. |
| **Code** | `POST /verify/code` | Python AST analysis and pattern rules (Python, JavaScript/TypeScript, Java, Go, SQL). `VERIFIED` once analysis completes; `is_valid` and `admission` say whether the code is safe. | None |
| **SQL** | `POST /verify/sql` | SQLGlot AST analysis against the supplied `schema_ddl`. `VERIFIED` when the query is valid or proven malicious; schema-parse failures and complexity-limit violations are `BLOCKED`. | None |
| **Schema** | Python library (`SchemaVerifier`) | Type, constraint, nested-object and array checks, plus inline arithmetic consistency checks on numeric fields using `Decimal`. `VERIFIED` once validation completes; `is_valid` says whether the data conforms. | None |
| **Image** | `POST /verify/image` | Width and height read from the image header. Only size and dimension claims can be `VERIFIED` (match) or `BLOCKED` (mismatch). | None from the API, which runs with the vision-model fallback off |
| **Consensus** | `POST /verify/consensus` | Runs several QWED engines on the same query: SymPy always; Python in the Docker sandbox at `high`; Z3 and, for average, mean, median or variance queries, Stats at `maximum`. `VERIFIED` only when every successful engine agrees, none is blocked and every contributing result is itself `VERIFIED`. | An LLM translates the query for the SymPy, Python and Z3 engines |

### Engines that never return `VERIFIED`

| Engine | Endpoint | Why not | Best possible status |
|--------|----------|---------|----------------------|
| **Fact** | `POST /verify/fact` | TF-IDF cosine similarity, keyword overlap, entity matching and negation detection are heuristics: two different claims can score alike. A supported claim is `UNVERIFIABLE` (`fact_verifier.heuristic_supported`); a negation conflict is `BLOCKED`. If deterministic confidence is below 0.7 and a provider is given, an LLM is consulted, and its verdict goes into `advisory_checks` only. | `UNVERIFIABLE` |
| **Stats** | `POST /verify/stats` | An LLM writes pandas code that runs in the secure Docker sandbox. Execution is not verification, so a successful run is `UNVERIFIABLE` with the observed result and a dataset fingerprint as evidence. Without Docker the request is `BLOCKED`; there is no in-process fallback. | `UNVERIFIABLE` |
| **Image (other claims)** | `POST /verify/image` | Numeric, colour, text and semantic claims need OCR or a vision model. In the Python library, vision-model output is recorded as an advisory check. | `UNVERIFIABLE` |
| **Reasoning** | Python library (`ReasoningVerifier`) | Cross-checks LLM interpretations of a query. Heuristic and LLM analysis is advisory only. | `UNVERIFIABLE` |
| **Symbolic** | Python library (`SymbolicVerifier`) | CrossHair (Z3-based) searches for counterexamples within a timeout. Finding none is not a completeness proof, so the result is `UNVERIFIABLE` (`symbolic_verifier.no_counterexample_found`). A counterexample or a timeout is also `UNVERIFIABLE`. | `UNVERIFIABLE` |

**Taint analysis** (AST data-flow tracking from sources to sinks) runs inside `CodeVerifier.verify_python_deep` in the Python library. `POST /verify/code` does not call it.

<Note>
`verification_mode` appears in two unrelated places. The Symbolic engine sets `developer_fields.verification_mode` to `symbolic` or `bounded_symbolic` to say which mode ran, and these results are never `VERIFIED`. `POST /verify/consensus` takes a request field `verification_mode` (`single`, `high` or `maximum`) that sets how many engines run. Neither is a trust label on the response.
</Note>

## Using this in production

Gate on `status` and, where the engine reports it, on `admission`. Treat `advisory_checks` as notes for a reviewer, never as a verdict.

```python
import requests

try:
    r = requests.post(
        f"{QWED_URL}/verify/sql",
        headers={"x-api-key": API_KEY},
        json={"query": sql, "schema_ddl": schema_ddl},
        timeout=30,
    )
    r.raise_for_status()
    resp = r.json()
except (requests.RequestException, ValueError) as exc:
    # No answer is not an ADMIT: fail closed.
    reject(f"verification unavailable: {exc}", None)
    raise

if resp["status"] == "VERIFIED" and resp.get("admission") == "ADMIT":
    run_query(sql)
else:
    # UNVERIFIABLE, BLOCKED, or VERIFIED · BLOCKED (proven unsafe)
    reject(resp["agent_message"], resp["developer_fields"].get("constraint_id"))

for check in resp["developer_fields"].get("advisory_checks", []):
    log_for_review(check["name"], check["details"])
```

For engines that never return `VERIFIED` (Fact, Stats, Reasoning, Symbolic), decide in advance what your application does with `UNVERIFIABLE`: route it to a person, keep the evidence in `developer_fields` as supporting material, or reject it.

## Trust boundaries in translated queries

When an LLM translates natural language into a formal expression, the solver can only check the translated expression, not whether the translation matches what the user meant.

### `POST /verify/natural_language`

An LLM translates the query into a math expression and SymPy evaluates it. This endpoint does not return `VERIFIED`: a successful evaluation comes back as `UNVERIFIABLE` with `constraint_id` `api.natural_language.legacy_conversion_failed`, and a mismatch comes back as `UNVERIFIABLE` with `math.legacy_inconclusive`. Use `POST /verify/math` with the expression itself when you need a `VERIFIED` result.

### `trust_boundary` on agent verification

`POST /agents/{agent_id}/verify` runs the same pipeline and returns a `trust_boundary` object that records what was and was not checked:

```json
{
  "trust_boundary": {
    "query_interpretation_source": "llm_translation",
    "query_semantics_verified": false,
    "verification_scope": "translated_expression_only",
    "deterministic_expression_evaluation": true,
    "formal_proof": false,
    "translation_claim_self_consistent": true,
    "provider_used": "openai",
    "trust_enforced": "VERIFIED",
    "attestation_policy": "mandatory",
    "overall_status": "VERIFIED"
  }
}
```

On this path a `VERIFIED` evaluation must be signed with an attestation bound to the translated expression. If signing fails, the result becomes `BLOCKED` and `trust_boundary.attestation_error` is set. `query_semantics_verified` is always `false`: even a `VERIFIED` result here covers the translated expression only.

### Numerical sampling fallback

When the Math engine's identity check cannot show two expressions equal by simplification or expansion, it evaluates both at fixed sample points. A match at every point is not a proof, so the engine returns `BLOCKED` with `is_equivalent: false`, `confidence: 0.0` and `method: "numerical_sampling_rejected"`.

## Design philosophy

> **"Probabilistic systems should not be trusted with deterministic tasks."**

QWED treats LLMs as **untrusted translators**:

1. An LLM may convert natural language into a formal specification.
2. A **deterministic check** decides the status of that specification.
3. The check runs on the translation, so a wrong translation can still produce a `VERIFIED` result for the wrong question. Any other model output is recorded in `advisory_checks` and cannot raise the status.
4. Where the translation step itself is not checked, the response says so (`constraint_id`, `trust_boundary`).

```
┌──────────────────────────────────────────────────────────────┐
│                        QWED Protocol                         │
├──────────────────────────────────────────────────────────────┤
│  Query → LLM (translator) → formal spec → deterministic check │
│                                                              │
│  Deterministic check passes     →  VERIFIED + proof_ref      │
│  Not provable / model-only      →  UNVERIFIABLE              │
│  Cannot run / policy violation  →  BLOCKED                   │
│  LLM, VLM or heuristic output   →  advisory_checks only      │
└──────────────────────────────────────────────────────────────┘
```

## Frequently asked questions

### Q: How do I accept only deterministically checked results?

**A:** Accept `status == "VERIFIED"` with a non-null `proof_ref`, and where the response has an `admission` field, require `ADMIT`. There is no request option that forces a symbolic-only path; engines that cannot produce a proof return `UNVERIFIABLE` or `BLOCKED` on their own.

### Q: Why is my supported fact claim `UNVERIFIABLE`?

**A:** The Fact engine's methods are heuristic, so it never returns `VERIFIED`. The scores, citations and any LLM opinion are in `developer_fields`, including `advisory_checks`, for you to review.

### Q: Is Consensus useful when it returns `UNVERIFIABLE`?

**A:** Yes. It runs the same query through several engines and reports `agreement_status` (for example `unanimous`, `majority` or `split`), `engines_used` and `confidence` in `developer_fields`. Disagreement between engines is a useful signal even when the outcome is `UNVERIFIABLE`.
